## Review freshness and transitions

**A [M]:** moderate_listing_reviewed locks listings and compares expected_revision AND expected_status, returning PT409 on conflict; then delegates existing moderation/audit. Approve requires pending_review, non-self authorized AAL2 staff, current policy acceptance in reviewed wrapper and all photos ready; result active has existing 30-day expiry. Reject requires a reason and remains nonpublic. Public visibility additionally requires active seller and unexpired active listing. Existing material edits on active/reserved/paused re-enter review; rejected content edits return to draft.

**R:** reviewed identity must cover category/version/model resolution, seller answers, common content/location, rental financials and review-relevant photo identity/order/cover. All such mutations take the same parent listing lock and advance revision atomically before returning; no-op updates do not. Staff resolution evidence binds to that revision and becomes stale on edit. Keep ordinary owner pending_review content edits denied by existing listings RLS. New family context/save operations currently require draft: extend their lifecycle only with the same re-review rules, including rejected correction, never direct active editing without review. The RPC revalidates family completeness and classification acceptance under lock before approval. On PT409 show refresh/re-review; never retry approval automatically.

This is necessary beyond the existing wrapper: [M] media operations explicitly permit pending_review changes but current re-review helper/reorder increments revision only for active/reserved/paused. No claim that expected_revision alone presently binds every reviewed byte. Recommendation: advance review identity for actual pending media changes without fabricating a new status transition. Preserve Goods submission checks and its existing statuses. Also close the unreviewed approval route for new families at the authoritative backend, including direct moderate_listing calls; a UI-only fix is insufficient. Any wider removal/change of the legacy RPC requires consumer-impact review.

**R:** public/owner/Admin render the same approved financial/answer meanings through explicit projections. Admin revalidatePath affects its own application, not Web caches. Verify fresh anonymous Web detail/search/related/favourites reads after approval, and absence after rejection/re-review; select a Web invalidation mechanism only if actual caching requires it. Do not claim cross-application cache invalidation is implemented.
