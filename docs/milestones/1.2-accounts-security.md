# Milestone 1.2 - accounts and secure Supabase foundation

## Gate

Reference contract only. Prerequisite: human acceptance of 1.1. First authorize PLAN ONLY, then review `docs/plans/1.2-plan.md` and explicitly authorize BUILD. Future files or this document grant no permission. Read the master reading map and shared workflow/verification procedures.

## Outcome

A real locally integrated Supabase application with confirmed email authentication, private/public profile separation, current account restrictions, and secure staff access. No marketplace features yet.

## Plan before building

Inspect accepted code and toolchain. Propose compatible Supabase CLI/SSR dependencies, Docker prerequisites, local stack resource needs, migration/testing strategy, allowed callback URLs, bootstrap method, and role/MFA tests. Installing Docker/system tools or accessing a hosted project requires separate authorization. Use a reproducible disposable local stack for development/testing.

Agree the narrow schema: public profile fields; private preferences/current account status; protected staff roles; initial audit and privacy-request records where used. Do not generate every future marketplace table. Document clean rebuild and upgrade-from-1.1 verification.

## Build in coherent batches

A. Local environment and schema: introduce Supabase config, versioned SQL migrations, RLS/grants, generated types from the applied schema, and validated runtime configuration. Separate local-only seed/bootstrap tools. Confirm the target before every destructive test reset; no remote reset.

B. Customer access: real email/password registration and confirmation through the local mail catcher; sign-in/out; recovery; secure session refresh; permitted profile changes; security/privacy pages. Validate inputs, redirect destinations, and errors without disclosing unnecessary account details. Keep future controls absent or honestly disabled.

C. Trusted access: ordinary server operations use request-scoped SSR clients and user sessions, never secret clients as an RLS bypass. Role/status values are protected from user-controlled metadata and columns. Public/profile APIs expose only intended public fields. Test direct Supabase requests.

D. Staff: separately authorized secure administrator bootstrap, MFA enrollment/challenge, privileged AAL enforcement in server/database paths, role assignments, minimal real staff access-management tools and audit. Never first-signup-wins. Test all staff roles and AAL1 versus AAL2.

E. Privacy continuity: implement a real user-owned data/deletion request submission/status record as appropriate to the approved schema. Clearly state manual processing is not yet implemented until 1.5. Preserve a safe access path for suspended users to security/privacy; avoid claiming support/appeals exist before 1.5. Current restrictions must affect already-issued sessions.

Add dependency-install and local-test scripts, local synthetic test accounts only, regression tests and documentation as each batch works. CI configuration may be added locally; activating remote repositories/secrets is a separate action.

## Required verification

Run prior checks plus local migration application, schema/RLS tests (pgTAP as appropriate), authenticated direct-API integration tests, and actual app/browser flows. Verify clean local setup and upgrade. Tests must not rely on a secret client to assert ordinary-user permissions.

Test: anonymous access denial; cross-user reads/writes; protected role/status changes; metadata-based escalation; invalid redirects; confirmation/recovery; logout; stale-token suspension; MFA missing/present; staff privilege boundaries; user-owned privacy requests; no private contacts in public responses. Use real isolated sessions and local mail delivery; no fake confirmation or recovery success.

## Exclusions

No listings/categories/media/search/chat, operational moderation cases, paid features, OAuth/SMS setup, hosted deployment, or broad schema stubs. Staff screens only support actual account/access workflows implemented here.

## Acceptance

- Local Supabase starts reproducibly and migrations/types match actual schema.
- Confirmed registration, login, recovery, profile changes and logout work with real local services.
- Private data and trusted roles/status are protected through UI and direct API paths.
- Staff privilege requires the right role and MFA; bootstrap is safe and documented.
- Suspended existing sessions lose prohibited capabilities without losing legitimate privacy access.
- Real database/integration/browser tests and prior scaffold regressions pass.
- Environment variables and service availability are represented honestly; no secrets are exposed.
- Progress/evidence and setup/security documentation updated; human review requested.

Stop after review handoff. Do not start 1.3 or connect a hosted database merely because local tests pass.
