# Milestone 1.1 - scope, design, and running foundation

## Authorization and outcome

Initial action is PLAN ONLY. Build only after the human approves the synchronized 1.1 plan revision and explicitly authorizes implementation. The complete marketplace remains the goal; this milestone deliberately delivers only its local foundation.

Read the active workspace rule, `docs/PROGRESS.md`, master section 0, `docs/BOOTSTRAP.md`, `docs/WORKFLOW.md`, and `docs/VERIFICATION.md`. Read master sections 1-5, 14, and 16-18 as needed. Use later feature sections for focused conceptual questions, not as a build backlog.

## A. Plan and prerequisites - before implementation

Inspect the existing workspace and applicable instructions. Detect the actual OS/shell/native versus WSL/container environment. Check already-installed Node/npm/pnpm and Git without changing the machine or printing environment secrets. Missing tool installation is a proposal, not a read-only action.

Write `docs/plans/1.1-plan.md` with revision r1, proposed scope, exclusions, safe scaffold/transfer procedure, dependencies, approval categories, small batches, test commands, and acceptance. Mirror the same scope/revision in the native Implementation Plan artifact. Update planning-status notes only, then stop for human BUILD approval.

No Supabase credentials, hosted project, Docker, email/SMS, or domain purchase is required. Do not install a package or download an executable simply to inspect its help during PLAN ONLY.

## B. Focused design documentation - after build approval

Create a substantive `docs/FOUNDATION.md` containing:

- Product boundary, configurable launch assumptions, anti-goals, and unresolved business decisions.
- Planned route map with the milestone that will implement each route.
- Architecture and data flow; textual or Mermaid explanation is sufficient.
- Conceptual entities and relationships, without executable SQL or fake generated types.
- Permissions matrix for anonymous users, owners, other users, participants, suspended accounts, and each staff role.
- Listing-state transition matrix: actor, prerequisites, moderation, expiry and visibility. Clarify reserved, sold, removed, material edits, and suspension.
- A threat checklist: account takeover, cross-account access, direct-API bypass, privilege escalation, unsafe uploads/caches, spam, excess staff access, and secrets.
- Original design tokens, responsive layout, accessibility approach, and verification strategy.
- Deferred controls and their later milestones, clearly labelled NOT IMPLEMENTED.

Keep README about what actually runs now. Do not duplicate the Project Bible or create a dozen empty documentation templates.

## C. Safe local scaffold

Use Next.js App Router, React, strict TypeScript, Tailwind, pnpm, and compatible lint/test tooling. Add only currently used dependencies. Follow the exact procedure in `docs/BOOTSTRAP.md`.

Default to a NEW lowercase temporary scaffold directory INSIDE the populated workspace and a collision-checked transfer of selected files. Do not run create-next-app at the populated root or blindly answer a conflict prompt. Skip unnecessary temporary installs/Git initialization and inspect unwanted generated agent-rule files. A reviewed manual setup is allowed when justified.

Preserve instructions and existing work. Set final package name `fairswap`; the final app must reside in the existing `FairSwap` root. Check every collision, merge intended configuration, verify at root, and clean up only the exact newly created temporary directory with appropriate permission. Record leftovers rather than forcing deletion.

Use a small actual structure such as `src/app` and a few reusable components, not speculative services or an unnecessary monorepo. Pin runtime/package-manager expectations and commit-ready lockfile content; do not make Git commits without approval.

## D. Working local page

Implement `/` with an original FairSwap.in wordmark, header, main content, footer, and responsive layout. Include a prominent development-foundation notice: accounts, listings, and communication are not connected yet.

Explain local classified buying/selling simply. Implement only genuinely working local interactions, such as an accessible mobile menu. Future search/post/account controls can be omitted or visibly disabled with explanations; they must not link to nonexistent features or fake success.

Add development-appropriate metadata, an original simple favicon, and an intentional 404 experience. Keep the incomplete scaffold out of search-engine indexing. Use system fonts or approved local assets; do not make the build depend on remote font/image downloads.

No fake advertisements, users, seller ratings, transactions, stats, or testimonials. Product photo fixtures and Supabase image allowlists are unnecessary in 1.1.

## E. Tooling and real verification

Create/update `.gitignore`, `.env.example`, README, and these actual package scripts:

- `pnpm dev`
- `pnpm lint`
- `pnpm typecheck`
- `pnpm test:unit` (non-watch)
- `pnpm test:e2e`
- `pnpm build`
- `pnpm start`

The page must build/start without Supabase values or Docker. Do not install future Supabase clients, generate dummy DB types, or validate unused environment variables at startup. Optional future variables can be blank comments only. Use installed-version-appropriate lint commands, not removed framework shortcuts.

Execute meaningful component tests for landmarks, the development notice, and any actual menu behavior. An empty suite or trivial always-true assertion is not adequate.

After approved installation of the project Playwright dependency, plan a Chromium-only binary download. Additional OS dependencies require separate actual-environment-specific approval. Keep command review enabled; a pending approval is not a failed test.

Configure Chromium projects for desktop (approximately 1440 x 900) and mobile viewport (approximately 390 x 844). Set Chromium explicitly for both projects; do not accidentally inherit a WebKit browser from a mobile device preset. These are viewport tests, not claims about actual mobile hardware or WebKit compatibility. Test the real app, not a mocked HTML page:

- Root loads with brand and development notice.
- No unintended horizontal overflow in either viewport.
- Implemented navigation works with mouse and keyboard.
- No fake account/admin/search links appear functional.
- No unexpected client/hydration errors.
- Unknown routes show the intended 404.

Capture screenshots and inspect them where available. Native browser tools supplement Playwright. Record capture/inspection separately and identify human review needed. Keep large reports gitignored; obey IDE access restrictions.

Before handoff run lint, type checking, unit tests, a production build, real production startup and Chromium tests against the current root app. Configure a test-owned server/port and prevent tests passing against a stale unrelated process. Stop only test processes this run created. Review changed files and `git diff --check` when Git exists. Do not use a successful unrelated command or pipeline tail as a test exit code.

## Explicit exclusions
